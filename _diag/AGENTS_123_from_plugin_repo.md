
## 一百二十三、独立应用（`app/`）：性能、内存、便携配置（2026-09-18，用户要求全面检查）

**用户要求原话**：「现在全面检查下性能开销，内存是否有泄漏，它的参数保存位置要跟DLL分开独立。
应用打算做便携版，所以配置文件直接放同目录。」

### 一、结论（先看这个）

| 项 | 结果 |
|---|---|
| **内存泄漏** | **无**。520 格滚轮 + 60 秒空闲，私有字节 / 句柄 / GDI / USER / 线程 **五个计数全部 +0** |
| **空闲成本** | **0.26% 单核**（250 Hz 引擎常转，不管有没有滚轮） |
| **滚动成本** | **约 1.5% 单核**（持续 31 格/秒时）；每格约 0.47 ms 单核时间 |
| **常驻内存** | **约 2.1 MB 私有**（`tasklist` 显示约 11 MB 是含共享页的工作集） |
| **配置文件** | **exe 同目录** `smoothwheelscroll-app.ini`，纯文本；与插件的 extstate **完全分开** |

### 二、便携配置（用户要求：放同目录）

- 路径由 **模块路径**（`GetModuleFileNameA(nullptr, ...)`）推出，**不是当前工作目录**——
  快捷方式、从终端启动、文件对话框都会改当前目录，按它写就会写到别处去。
- **有意不与插件共用存储**：插件把 4 个参数存在 REAPER 的 extstate（`reaper.ini` 的
  `SmoothWheelScroll` 段）；app 存自己的文件。**共用会导致更新一个产品悄悄改掉另一个的手感。**
- **读写都过 `Clamp()`**（单一来源），坏值进不到模型。
- **退出时总是重写一遍**：手工编辑过的文件会被规范化成 app 认的形状；首次运行也因此留下一个可编辑的文件。
- **写文件是原子的**（临时文件 + `MoveFileEx` 替换），写到一半被打断不会毁掉好文件。
- 托盘菜单加了 **`Settings file...`**，直接打开它（不存在就先写一份）。

### 三、★ 顺手修掉一个真 bug：`atof("abc")` 会把参数甩到**端点**

- **原实现**：`glide = atof(val)`。`atof("abc")` = **0.0**，而 0.0 过 `Clamp()` 正好是该参数的**最小值**
  —— 于是**打错一个字，参数就被静默送到量程尽头**，与 config.h 里写的"坏值忽略、保持默认"**正好相反**。
- **修法**：`ParseNumber()` 严格解析（必须至少有一位数字、整串必须消费完、指数必须成形），
  解不出就**保持原值**。附带好处：`150ms` 不再被读成 `150`。
- `enabled` 同样加了 `ParseBool()`（认 1/0、on/off、true/false、yes/no），别的写法保持原值。
- **门**：`test/check_app_config.sh` 的旧断言**把这个 bug 当成正确行为写死了**
  （`ramp=oops` → 落在下限），已改成断言正确规则；另加 `150ms`、`banana` 两个用例。

### 四、★ 测量踩到的坑（**差点得出错误结论**）

**第一次负载测试报「零增长、每次滚轮 0.13 ms」——那是假的：那些滚轮根本没进 app。**

- app 的自环防护**正确地**丢弃了 `LLMHF_INJECTED` 事件；而**任何程序**用 `SendInput` 合成的滚轮
  **同样带这个标记**（对 app 来说两者无法区分）。于是探针滚了 120 格，app 一格都没处理，
  测的是一个**完全空闲的进程**。
- **修法**：加**测试专用**开关 `SWS_APP_ACCEPT_INJECTED=1`，**只解除标志检查**，
  `g_injecting` 那道保持——**自己的输出仍然被丢，自环起不来**。启动日志会写明 `[TEST MODE: ...]`。
  出货默认不变（不接管注入事件）。
- 打开后真实成本才显出来：**每格 2.47–2.91 ms**（原先测出的 0.13 ms 是空转）。
- **教训：性能测试必须先证明"被测路径真的被执行了"**（看日志计数），
  否则"零泄漏"可能只是"零工作"。这条与 §16 第 2 条（"探针不能挂在不存在的机制上"）同类。

### 五、另一件事：线程数 6 → 3 不是泄漏

- 两轮采样都看到线程从 6 掉到 3（**只减不增**，且启动约 17 秒后发生），一度像是"线程被回收"。
- 判定：**泄漏是往上爬不回落的，"变少"不是泄漏**；而且 6 与 3 出现在同一次生活的不同时刻，
  稳定在 3 之后**再没变过**（60 秒逐秒采样，线程列唯一值只有 `3`）。
- 那 3 条是 app 自己的：**主线程 / 引擎线程 / 注入线程**。
- `_diag/thread_owner.cpp`（按起始模块归名）**没做成**——`NtQueryInformationThread` 的信息类
  在这台机器上一直返回 `0xc0000004`（缓冲区/类不匹配），换个角度又回到"数数"上了。
  **没有继续钻**：计数证据已经足够（只减不增、稳态 60 秒不变），
  且这条探针**只用于诊断、不进任何门**。要重做请从"线程起始地址"换思路（如 ETW）。
- `_diag/app_soak_probe.cpp` 报的线程数与 PowerShell 曾不一致（同一时刻 3 vs 6），
  原因是两者**取样的瞬间不同**（快照 vs 枚举），不是哪个错了。
