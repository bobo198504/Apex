# 构建与门的实测代价（AGENTS 分册）

> **何时读我**：构建慢了、门跑太久、想知道某个数字是怎么量出来的，或者要动 apex/build.sh 与 test/run_all.sh。
>
> 本册是从根目录 AGENTS.md 拆出来的正文，**内容与拆之前逐字相同**（只是搬了家）。根目录那份末尾有索引；
> 判据与理由都在正文里 —— 不要在这里写摘要，摘要会漂移，正文不会。

## 一之二、★ 版本记录：`versions\<版本>\`（**这个项目没有仓库**）

**Apex 没有 git**（拆出来时用户没要求建仓），所以**源码没有版本控制兜底**。
`versions\<版本>\` 就是它唯一的历史，改坏了要能回到那里。

```
versions\1.0.0\
  MODEL.md   ← 这一版做了什么、指纹表、三层各在哪、构建与验收、已知边界
  src\       ← apex\ + common\ + features\SmoothWheel\ 的**原样拷贝**（目录压平一层）
  bin\       ← apex.exe / apex-settings.exe / Plugins\SmoothWheel\SmoothWheel.dll
```

- **`changelog` 在仓根 `CHANGELOG.md`**，规范见 §八。**只写"改了什么"**，一条一行，中英双份。
- **指纹表是给"回到这里"用的**：`MODEL.md` 里每个文件都有字节数与 md5，可以逐个对回仓里的文件。
  **⚠️ 指纹不更新比没有更糟**——它说"已核对"而没人核对（同 §3.1 的 `shared/SOURCE.md`）。
- **`shared/` 不进快照**：那三个头是**插件项目**的文件，指纹在 `shared/SOURCE.md`；抄一份只会多一个会漂移的副本。
- **新版本 = 新的文件夹**，不要覆盖旧的。**是否建仓、是否发布，都要先问用户**（§零之二）。
- ⚠️⚠️ **"刷新快照"不是 `rm -rf` 再抄一遍。**（2026-09-18 我真这么干了，把唯一一份 1.0.0 删了。）
  **这里的源码没有第二份**：`versions\` 是唯一的历史，删掉就只剩二进制。
  - **要更新快照，先建新版本号**（1.0.1），旧的**一个字都不动**。已交付的那一版是历史，不是草稿。
  - **万一删了**：`bin\` 里的产物可以从**用户正在运行的部署目录**（`D:\App protable\Apex`）取回，
    前提是那份还没被覆盖 —— **指纹表就是用来确认"取回的是不是原件"的**。
  - **源码可以靠"能否复现产物"来验证**：`rm -rf build/apex/obj && bash apex/build.sh`，三个产物
    逐字节相同即证明**代码**没走样。⚠️ **但这不证明文本相同**（注释找不回来）。能证明的与不能证明的，
    必须分别写清楚——1.0.0 的 `MODEL.md` 里就是这么记的。
  - **`panel.html` 是特殊情况**：它作为 `RCDATA` **嵌在 `apex-settings.exe` 里**，所以从产物能**逐字节**
    取回（`build/_extract.exe` 那类的抽取器，资源 id 256）。这是唯一一份能从二进制完全恢复的源码。


### 2.0.1 ★★ 交付＝一条命令、只停一次（`deploy.sh --gated`）

用户的要求：「**部署直接停掉正在运行的实例，一次成型**」。

**为什么以前要停两次**：装配层的门必须独占现场（它们注入真实滚轮输入，两个宿主同时挂钩会打架），
所以 `run_all.sh --assembly` 停一次、跑完再把 Apex 起回来，紧接着 `deploy.sh` 又停一次去复制——
用户看到的是自己的 Apex 眨两次眼，而文件只替换一次。

**现在**：`bash apex/deploy.sh --gated` = 构建 → 门（`APEX_KEEP_FIELD=1`：**门绿就把现场一直占着、不还**）
→ **再构建一次 release** → 复制 → 启动。**一次停机、一次启动。**

⚠️ **"绿了才不还"是这个模式的全部要点**：`test/run_all.sh` 的 trap 写成 `[ "$fail" -eq 0 ] || apex_restore_the_field`，
所以门红、Ctrl-C、崩溃——任何失败路径都**把用户的程序还回去**。`test/lib_procs.sh` 的提示语也跟着改
（这个模式下它不能再说 "will be restored at the end"）。

⚠️ **两次构建，而且第二次是必须的**（第一次跑这个模式就撞上了）：门里有门会跑**非 release** 构建
（`check_apex_modular` 编译功能做边界测试等），而普通 `build.sh` 会把 **dev-only 的 `AuditStub.dll`**
放回产物——复制前的检查于是拒绝发货，而那时现场已经被门占着，用户的 Apex 就留在了停机状态。
所以 release 构建永远是**复制之前的最后一件事**（增量，约 1 秒）。


### 2.1 ⚠️ 迭代速度是设计的一部分（2026-09-18 起）

用户原话：「开发过程有点慢，特别是反复验证环节。」**这是要修的缺陷，不是抱怨。** 三条已落地：

1. **构建转为增量**（`build/apex/obj/` 保留，不再每次清空）。判据是**目标文件比源码旧、或有头文件比它新**。
   - 全量 8 s → 改一个 .cpp **3 s** → 无改动 **1 s**。
   - ⚠️ **踩过的坑**：最初用 `find -printf '%T@'` 取最新头文件时间戳，**结果是空的**——因为
     `build.sh` 为了 g++ 把 w64devkit 放进 PATH，而它自带 **BusyBox 的 `find`**，**没有 `-printf`**。
     于是标记文件为空、每个目标文件都比它旧、**增量静默失效**（还在"正常工作"的样子）。
     现在用 `find -newer FILE -print -quit`，两个 find 都支持，不需要时间戳运算。
   - **失效时怎么强制全量**：`rm -rf build/apex/obj`。
2. **门的等待从固定 sleep 改成等条件**。端到端门 24→17 s，图标门 10→7 s。
3. **门分两层**（2026-09-19，见 §五）：编辑循环只跑**构建层**（约 35 秒，不起进程、不碰输入设备）；
   **装配层**（起真程序那 8 扇）只在交付前跑一次。构建层单独跑完会打印 "BUILD LAYER OK"，
   **不会伪装成交付通过**。

### 2.2 ⚠️ 起一个进程在本机要 0.15 秒（2026-09-19 实测）

这条不是常识，是**量出来的**，而且它决定了门该怎么写：

- `$(basename "$f")` × 29 次 = **1.3 秒**（`${f##*/}` 是 0.1 秒，**快 12 倍**）
- 一次 `g++ -E` = 0.15–0.24 秒；17 个文件逐个跑 = 1.1 秒，**合成一次跑 = 0.46 秒**
- 一次 `powershell -NoProfile` = **0.39 秒**（所以脚本里每多一次 PowerShell 调用，就是实打实的一秒）

→ **判据**：门里做机械判断时，**别每个文件起一次进程**。读文本用一次 awk 全扫完
（`test/proc_rules.awk` 就是照这条写的，把第 7 节从 11 秒压到 127 毫秒）。

### 2.3 ⚠️ stderr 必须干净，否则"成功"和"失败"分不出来（2026-09-20 实测）

**现象**：`deploy.sh --gated` 24 扇门全绿、产物复制完、程序起来了，**退出码却是 1**。
用户看到的是一份"看起来失败"的部署，而每个步骤都过了。

**原因不在脚本里，在调用方式上**：PowerShell 把子进程的**每一行 stderr 都当成错误记录**，
而错误记录会让它自己的退出码变成 1——**哪怕那个进程返回 0**。实测：
`bash -c "echo warn 1>&2; exit 0"` 从 PowerShell 走一遍，拿到的是 **1**（同一个命令直接跑是 0）。

**两个来源**：① AutoIME 的 Rust 命名警告（`AutoIME` 不是 snake_case）；② **cargo 自己的进度**
（`Compiling` / `Finished`）——**它本来就写 stderr，这是设计如此**，所以即使没有那条警告，
失败的样子也不会消失。（一开始我把账全记在警告上，是错的；是量完才看清的。）

**修法两条**：`features/AutoIME/Cargo.toml` 里 `[lints.rust] non_snake_case = "allow"`（名字是**产品名**，
文件必须叫 `AutoIME.dll`，改不了；注释写在那两行旁边，而不是 `lib.rs` 里）；
`build.sh` 的 cargo 加 **`--quiet`**（压掉的是 cargo 的日志，**rustc 的 warning/error 照旧输出**——
把警告放回去重建验过）。

→ **判据**：**构建/部署路径上不许有任何非必要的 stderr 输出**。stderr 一旦常年有东西，
"退出码非零"就不再是信号。要留诊断信息就写到 stdout 或自己的日志里。

### 2.4 ⚠️ Rust 的产物不可字节复现，C++ 的可（2026-09-20 实测）

同一份源码、同一个命令，重建两次：**AutoIME.dll 有 3 个字节不同**（偏移 136 / 216 / 2828804，
大小一模一样 4497810）；而 C++ 那三个产物**逐字节相同**。

→ **判据**：md5 比对只在**"刚复制完"那一刻**有意义（`deploy.sh` 正是这么用的：复制后比 build 与部署），
**绝不能**用"重建之后 md5 变没变"来判断代码有没有改——它会永远告诉你"变了"。
