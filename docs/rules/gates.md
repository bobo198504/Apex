## 五、门（`test\run_all.sh` 跑全部，分两层）

**⚠️ 门分两层，因为它们要回答的不是同一个问题**（用户要求："缩减没必要的反复测试流程 ... 数据模型验证可以由你在构建时就要做好，不要拿到部署后来验证"）。

```bash
bash test/run_all.sh              # 构建层：编辑循环用，几十秒，不起进程、不碰输入设备
bash test/run_all.sh --assembly   # 构建层 + 装配层：交付前跑一次
```

### 5.0 ★「这个进程是我的吗」只有一个实现：`test\lib_procs.sh`

**所有**门和探针的清理都走它，不再各自抄一份（`apex_own_pids` 列 pid、`apex_kill_own` 杀）。
理由就是 §七那条"一条规则只能有一个实现"：那句过滤器曾被抄进**九个**脚本，而**抄出去八份的规则，
你只修好了手上这一份**。

判据（也是 `check_apex_modular.sh` 第 7 节机器验的）：

1. **名字 + 路径，两个条件缺一不可。** 名字单独不够（`/IM apex.exe` 杀掉用户正在跑的那份），
   路径单独更不够（那句临场敲的 `Get-Process | Where-Object Path -like '*App protable*'` 杀光了用户的
   托盘工具——不带 `-Name` 的 `Get-Process` 返回**全机器**进程）。库还**拒绝**空片段和"既不是
   `_` 开头的临时目录、也不是我们自己编的 exe 名"的片段：**空片段不是"不过滤"，是"全都匹配"**。
2. **配套的还有"启动了就得能停"**：脚本里 `start "" <exe>` 出现的每个 exe，都必须在这个脚本的
   名字表里（或落在库的默认集合 = 两个宿主 exe）。这条抓过两回：`check_apex_flash` 起了面板不杀面板，
   于是下次运行报"上一轮的目录删不掉"——**看起来像磁盘问题，其实是残留进程**。

⚠️ **这套检查自己也要能被验。** 它靠读脚本文本来判断，而它读的是**自己写的模式串**，
所以它必须给自己两个豁免（本文件、以及它自己的源码文本）——而**豁免必须配一个自检**：
那里真的喂两个夹具给规则，一个**必须命中**（真实的调用点）、一个**必须不命中**（正则字面量），
失败就报 FAIL。**光有豁免没有自检，就是"除了自己那一个文件，别的都管"。**

⚠️ **规则本身搬进了 `test/proc_rules.awk`，因为它太贵了。** 原来是一个 bash 循环，每个脚本要起六到八个进程
（`grep`、`awk`、`basename`，还有**为每个 exe 名起一次 `echo | grep`**）。本机**起一个进程约 0.15 秒**
（实测：29 次 `basename` = 1.3 秒），二十来个脚本就是**十一秒**在算字符串。一扇要花十一秒回答机械问题的门，
迟早会被跳过——而那正是用户要求砍掉的东西。同一个 awk 程序跑全树：**127 毫秒**。
**判据**：机械判断不要每个文件起一次进程；`basename` 用 `${f##*/}`，`grep` 用一次 awk。

### 5.0.1 ⚠️⚠️ 工具的坑：Git Bash 会把 `/` 开头的参数改写成 Windows 路径

**这是 2026-09-19 抓到的，而且它把一扇门整个变成了空转。**

- 每扇门都 `export PATH=".../w64devkit/bin:$PATH"`，于是 `sed` 是 **w64devkit 的 `sed.exe`——原生程序，不是 MSYS 程序**。
- Git Bash 在把参数交给**原生程序**之前，会把**以 `/` 开头**的参数当成路径改写：`sed '/^$/d'` 到了 sed 手里
  变成 `C:\Program Files\Git\^$\d`，sed 回一句 `unsupported command C`。
- **在管道里这个错误是隐形的**：`a | sed '...' | sort` 的退出码是**最后一个命令**的，所以错误照打、状态照 0、
  那一段**什么都不输出**。第 7 节的覆盖面因此空了，却给 25 个脚本印了 ok。

**判据**：

- **别写 `sed '/^$/d'`**，写 `grep -v '^$'`（`s/.../.../` 不受影响，因为它不以 `/` 开头）。
- `awk '/x/ {print}'` **是安全的**，但**不是因为 awk 特别**——是因为**花括号让 MSYS 不动它**。别把这个当规律记。
- 第 8 节现在**活着验**：同一个 PATH 下真跑一次 `sed`，并且**全树扫**有没有脚本又把
  `/` 开头的 sed 脚本递给原生工具。**它同时把那句"被改写"的效果打出来当注脚**——
  哪天真的不烂了，那行会自己说出来，这条规矩就能凭证据退休。


⚠️ **第四条第 4 条规矩：门里启动的长期进程，输出必须重定向**（2026-09-18，套件因此挂了两次）。
`run_all.sh` 用 `out=$(bash "$script" 2>&1)` 采集每个门的输出，而**命令替换要等到管道的所有写端关闭**才返回。
`cmd //c start` 自己立刻返回，但它拉起的宿主**继承了那条管道**——宿主活多久，`$( )` 就等多久。
表现是：门其实**已经跑完并通过**（接收方报告躺在文件里），但不打印任何东西，看起来像卡死。
**凡是在 `$( )` 里启动的、比函数活得久的东西，都要 `>/dev/null 2>&1`。**
（原来用 `read < <(RunOnce ...)` 没事，因为 `read` 读到第一个换行就返回、不等 EOF——换成 `$( )` 才致命。）

⚠️ **门的四条硬规矩，都是踩出来的**（2026-09-18 / 09-19）:

1. **绝不按进程名杀。** `taskkill /F /IM apex.exe` 会杀掉**用户正在跑的那一个**——门自己把用户的会话打掉了。
2. **⚠️⚠️ 也绝不按"路径片段"杀，必须"进程名 + 路径"两个条件。** 这一条比上一条更狠，因为它**杀的不是
   Apex，是用户别的程序**。2026-09-19 实际发生过：一句临场敲的
   `Get-Process | Where-Object { $_.Path -like '*App protable*' }` —— **`Get-Process` 不带名字就是全机器
   所有进程**，而 `D:\App protable\` 下有**36 个便携工具**，于是那一瞬间正在跑的**全被强杀**。
   （用户原话：「怎么把我其它托盘应用关了，谁给的权限？」**没有任何人给过**，就是过滤器写松了。）
   **做法**：**调库，不抄形状**——`. "$ROOT/test/lib_procs.sh"` 之后用 `apex_own_pids` / `apex_kill_own`。
   那句过滤器曾在**九个**脚本里各有一份，所以这条现在**机器验**（第 7 节）：脚本里出现自己的
   `Get-Process` 查询就 FAIL，杀了进程却没 source 库也 FAIL。判据与理由见 §5.0。
3. **绝不写 `build\apex\` 里的设置文件。** 门曾经把自己的 `apex.ini` 覆盖上去、把日志删掉——那是用户被
   告知可以直接运行的文件夹。要钉配置就**拷一份到自己的目录**再钉（见 `check_apex_endtoend.sh`）。
4. **共享设施按身份归类，不按进程名。** `msedgewebview2.exe` 全世界都在用，判"是不是我的"只能按
   `--user-data-dir`（见 §6.1）。

⚠️ **没有一扇门会解析宿主发给面板的快照**，而这正是踩过的地方：删掉 `skip` 数组后留下双逗号，
`JSON.parse` 直接失败，页面显示"宿主未运行"——宿主其实每条消息都答了。
**看到"宿主未运行"时，第一件事是去看面板日志里的 `document` 行，而不是怀疑宿主死了。**

### 5.0.2 ⚠️⚠️ 部署只换程序，绝不碰用户数据（2026-09-19，**真的删过用户的东西**）

`apex/deploy.sh` 第一次真跑，就**删掉了用户的 9 条 AutoIME 规则**（`Plugins/AutoIME/config.json`）、
SmoothWheel 的设置和捕获历史。

**怎么删的**：拷 `Plugins/` 那一步写的是 `rm -rf "$TARGET/Plugins"` 再拷新的。这个写法对**退役功能**是**对的**
（树里删掉的功能必须从部署目录消失，否则那份旧 DLL 会一直跟着跑），对**同目录里别的东西**是**灾难**——
而 `config.json` 就在同一个目录里。

**最刺眼的是**：脚本自己往下两段的注释里已经写着"config.json 属于用户，部署永远不写它"。
**`rm -rf` 把注释里那句话直接推翻了。**
→ **一处泛泛的清理，不是删除某个具体东西的安全做法。**

**现在的判据**（`check_apex_deploy` 机器验，跑的是真脚本、扔进一个临时目录）：

1. **只替换程序自己的文件**：`.dll` 和随它发布的 `.ini`。同目录里别的一切（`config.json`、`observed.json`、
   捕获历史）**原样不动**，门用 md5 逐字节比对。
2. **退役功能整个文件夹删掉**（那是唯一该删的整目录：功能都没了，里面没有用户数据）。
   两个方向都要验：**该删的删了**，且**不该删的没删**——只验前者的话，"干脆什么都不删"也能过。
3. **只有"看着像 Apex 的目录"才接受**（有 `apex.exe`、或 `Plugins/`、或 `WebView2/`）；
   别的目录一律 REFUSING。这是为了防"路径敲错一个字母，把程序撒到用户别的工具目录里"。

⚠️⚠️ **而「验部署」的门自己不许跑部署的副作用（2026-09-19，同一天第三次）。**
`check_apex_deploy` 要验的是**文件语义**（拷了什么、换了什么、没动什么），那全是目录的事实，
**不需要一个在跑的程序**。可第一版它直接跑整个 `deploy.sh`，而那个脚本的**第 2 步清场、第 4 步启动**——
于是这扇**住在构建层、声称"不起进程"**的门，把**用户正在跑的那份 Apex 停了**，又起了自己的一份，
再按路径把自己那份杀掉。用户回来时 Apex 已经没了。
→ 修法是 `deploy.sh` 认一个 `APEX_DEPLOY_FILES_ONLY=1`（跳过第 2、4 步），门设上它，
并且**门里断言这个开关真的被遵守**（输出里必须有那句 SKIPPED），否则"门不再起进程"就只是一句口号。
**判据**：一扇门如果必须借用一个有副作用的脚本来验它的一半，**那一半就该有开关**；
开关还要**被门自己验一次**，因为一个没人检查的开关等于不存在。

⚠️ **同一批还带走了一份用户数据，是同一个 `rm -rf` 的第二次伤害**：`Plugins/SmoothWheel/SmoothWheel.ini`
（用户调过的 glide/slow/ramp/top 和黑名单）也一起没了。恢复它靠的是 **`apex-settings.log` 里最后一份完整
控件文档**——那是宿主向面板报告"功能当前载入的是什么"，是当时唯一留下的记录。
**这一条的意思是**：日志不只是排障用的，**它是被删掉的用户状态的最后副本**。别把它当噪音清掉。

### 5.0.3 ⚠️⚠️ 任何自动化都不许碰用户的鼠标键盘（2026-09-19，用户投诉）

用户原话：**"部署时，不要抢鼠标，以及其它相关输入，除非是功能必须的"**、
**"一切UI交互测试都由我来做，我会反馈给你。能直接跑的算法数据可以由你来测。"**

**犯过的事**：`_diag/apex_inject.cpp` 开头有一句 `SetCursorPos(x, y)`。它来自更早的设计——那时接收器是
"把指针拖到测试点"；后来接收器改成**建在光标周围**（指针只读不写），这行**没跟着删**。
于是端到端门每跑一次，**用户的光标就被拽回去一次**。用户报的"每次部署都在抢用户鼠标"就是这个，
而**读意图永远看不出来，只有打开那个工具才看得见**。

**判据**（`check_apex_modular` 第 9 节机器验）：

1. **门（`test/*.sh`）一律不许动输入设备。** 扫 `SetCursorPos` / `mouse_event` / `keybd_event` /
   `SendInput` / `MOUSEEVENTF_LEFT|RIGHT` —— **注释先剥掉再扫**（第一版没剥，于是报了三支"在注释里说明
   自己不用它"的工具 + 它自己，全是我自己的误报）。
2. **会动输入的工具必须在文件头自称 `MANUAL-ONLY`**，只留给用户**手动**跑。
   `WHEEL-ONLY` 是给"只注入滚轮、不碰光标"的那几支（那是产品自己的输出，门就该用它）。
3. **`apex_click` / `apex_drag` 会真点真拖**——封存，永不进任何自动流程。它们留着是因为
   **有些坑只有真点才发现**（"开关不能用"是 CSS 把点击吃掉了，DOM 桩永远查不到），但**跑它们是用户的活**。

⚠️ **"用完把光标放回去"不算合规。** 放回去比不放回去好，但标准是**根本不动**——
被拽走一秒再弹回来，仍然是被拽走了一秒。

### 5.1 端的探针（在 `_diag\`）

- `apex_panel_probe.js` — **不用开窗口**跑面板脚本（DOM 桩）。上面 §3.5 的前两条就是它抓的。
  `node _diag/apex_panel_probe.js`
  （它读的是 `apex/ui/panel.html`；曾长期写着拆分前的 `app/apex/ui/panel.html`，于是整支探针跑不起来。）
- `test\lib_procs.sh` — **不是探针，是所有门/探针共用的那一句"这个进程是我的吗"**（§5.0）。

  ⚠️ 片段必须是**本脚本自己的临时目录**（`_` 开头）或**我们自己编的 exe 名**，库会拒绝别的写法。

  ```bash
  bash -c '. test/lib_procs.sh; apex_own_pids ""; apex_own_pids "protable"'
  # 两句都应该被拒绝并打印原因，而不是列出进程
  ```

  `check_apex_icons` 的核心；也能当诊断用：任意 exe + 编号都能看。

- `apex_broadcast.exe`（源码 `apex_broadcast.c`）— 广播 `WM_SETTINGCHANGE`/`ImmersiveColorSet`。

- `apex_receiver.cpp` / `apex_inject.cpp` — 端到端门用的"受控接收器"与"精确注入器"
  ⚠️ **接收器必须做到三件事，而且都有过用户投诉**：不画（分层、alpha **1**）、不开控制台（`-mwindows`）、
  **不动鼠标**（窗建在鼠标周围，而不是把鼠标挪到窗上）。见 §6.7 与 §6.8。
- `apex_window_watch.exe`（源码 `apex_window_watch.c`）— **轮询枚举可见窗口**，回答"测试到底有没有在你屏幕上弹窗"。
  别改成"首尾各采一次"：接收器只活约 2 秒，夹在中间，diff 看不见它。
- `apex_panel_shot.exe`（源码 `apex_panel_shot.cpp`）— **截面板自己的窗口**（按进程+类名找，`PrintWindow`），

  （这个坑 DARK_TITLEBAR.md 里记着）。⚠️ 输出是 **BMP**，不是 PNG：GDI+ 在这套 MinGW 上 `Save` 会**段错误**，
  而那时图早就抓好了，看起来却像"抓不到窗口"。要 PNG 用 PowerShell 转。
  **它还会打印抓的是哪个 pid 和哪个路径**——曾经抓到残留的旧进程，截出一张旧 UI 而没有任何提示。
- `apex_click.exe`（源码 `apex_click.c`）— 在指定窗口的客户区**点几个点**，用于验证"真的能用鼠标切页"。
  **点完把鼠标放回原处**（这个项目已经因为工具偷走鼠标被投诉过一次）。坐标是**客户区**，
  而 `apex_panel_shot` 的采样坐标是**含标题栏的**——两者差约 31px，混用会点空。
- `apex_drag.exe`（源码 `apex_drag.c`）— **按住拖动**（按下→移动→松开），用于滑块。
  `apex_click` 只在原地按一下，对滑块没用：range 控件是**按住并移动**时才报 `input`。
  ⚠️ **点空了两边都是"失败"**：坐标差 31px 时它照样报 `clicked 1 point(s)`，只是什么都没发生。
  所以验证要看**效果**（宿主/面板日志里的消息、界面上的数值），不要看工具的退出码。
- `apex_hit_probe.cpp` — 面板开着时问一句：**光标下的那个点，属于哪个进程、哪个顶层窗口**。

  `msedgewebview2.exe`、顶层是 `ApexSettingsWnd`，所以判据必须取 `GA_ROOT`（§3.6.3）。

- `apex_close_probe.cpp` — 按 **PID** 给宿主发 `WM_CLOSE`（和托盘"退出"、面板"退出"是同一个消息）。

  **它只认你给的 pid**：本机有一份真在跑的 Apex，按进程名的工具会打到它。
- `apex_edit_probe.cpp` — 模拟面板发**一条设置修改**（走真实协议 `settings_ipc.h`），

  ⚠️ **值可以用 `@文件` 给**，那不是图方便：这是 MinGW 控制台程序，**C 运行时按 ANSI 解命令行**，

  面板本身不走 argv（发的是 JSON 字节），所以门要把"面板会发的那些字节"写进文件再指过来——**一个字节都不差**。
- `apex_palette_probe.js` — 读 `apex/ui/panel.html` 算配色：说明暗两条路是否声明同一套、层次顺序、
  对比度（WCAG）、以及饱和度是否真的比被否掉的那版低。**不开进程，秒级。**
  ⚠️ 它是**脚本文件**，所以参数在 `argv[2]`（`node -e` 里才是 `argv[1]`）——写成 `argv[1]` 会去读自己。
- `caption_brightness.ps1` — 量标题栏亮度（**别靠眼睛看截图**）
- `DARK_TITLEBAR.md` — 暗色标题栏的实测结论与**我犯过的错**

## 六、已知的坑（都是实测，不要重走）

1. **`msedgewebview2.exe` 是共享设施。** 系统里可能有十几个（Edge、Waves 插件、系统组件都在用）。
   判断"是不是我的"，**必须按 `--user-data-dir` 归类**，不能数进程名。
   实测：一度看到 18 个进程 491 MB，**属于 Apex 的是 0 个**。
2. **面板开着的开销约 152 MB（6 个浏览器进程），关闭即释放到 0。** 宿主常驻 2.4 MB。
3. **测试窗口要 `WS_EX_TOPMOST`。** 端到端门曾报"0 deltas"——不是代码回归，
   而是注入点被别的窗口盖住了（我开的 PowerShell）。接收器现在会**自报"光标下是谁"**。
4. **`FindWindowW` 在本机对 `RegisterClassA` 注册的窗口不可靠**（能找到 `Shell_TrayWnd`，
   找不到自己的）。产品代码用 A 系列（IPC 一直正常）；**测试脚本也要用 A 系列**。
5. **PowerShell 的 `$Pid` 是自动变量**，不能当 `param()` 的名字。
6. **`python`/`python3` 在本机是 Store 空壳**，不能用。用 `node` 或 `awk`/`sed`。
7. **文件里行尾反斜杠是行连接符。** 注释里写目录树 `Plugins\` 会把下一行函数签名吞掉
   —— 这个坑在 `paths.h` 上真的发生过。
8. **⚠️ 分层窗口 alpha=0 会漏鼠标。** `WS_EX_LAYERED` + `SetLayeredWindowAttributes(..., alpha=0)`
   确实看不见，**但那个区域不再接收鼠标消息**，直接穿透到下层窗口。
   实测：接收器报 `under cursor : SysListView32`，滚轮全打在桌面上。
   **要"看不见但能接住"，alpha 用 1**（1/255，肉眼无差别）。
9. **⚠️ 别把用户的鼠标挪走。** 端到端门的接收器原来是"把光标移到测试点"，
   等你一动鼠标，注入的滚轮就打到**你的窗口**上，接收器数到 0，门就报"代码坏了"。
   实测：三次滚轮只有一次落到接收器。**正确做法是反过来——把窗口建在光标周围**，
   并且**在退出前自检"光标还在不在我身上"，不在就宣布这次测量无效**（`valid: yes/no`）。
   一个会因用户正常工作而**谎报**的测试，比没有测试更糟。
10. **门要读的字段名，改的时候要连着门一起改。** 接收器把结束行从 `exit:` 改成 `done:`，
    门还在 grep `exit:` —— 于是它把 115 条消息读成 0，报了一场不存在的回归。
    现在门按**行形状**匹配（`wheel messages`），不认第一个词。
11. **⚠️⚠️ 断言"一串东西"时，必须顺带断言"它是几个"** —— 否则 **join 会把"根本没分割"伪装成"分割对了"**。
    实测（2026-09-23）：把 `QuickOrderSetFromKeys`（`hostconfig.h`）里的逗号**故意删掉**之后，
    `check_apex_hostconfig.sh` 照印 `ok`，因为它的断言是"把键**用逗号 join 起来**的那串文本"，
    而"一条都没分割的整串"打印出来**逐字相同**。同一轮里 `check_apex_persist.sh`（数文件行数）抓住了它。
    → 探针里现在多一句 `quickOrderN == 2`，并写在注释里。**判据**：只要断言里出现"拼接/序列化后的文本"，
    旁边就得有一句**数量或形状**的断言（见 `docs/rules/quickpanel.md` 那一节的完整链条）。



## AGENTS.md 的体积：一条会自己长大的规矩（2026-09-20 实测）

**现象**：`AGENTS.md` 一路加到 **126,676 字节**（1,474 行），而一次会话能读进去的指令预算约 **65 KB**。
**实际后果**：超过一半的内容**根本到不了眼前**——本次会话只加载到 §3.7.4，那之后的
`§四 绝对红线`、`§五 门`、`§六 已知的坑`、`§七 变更纪律` **一条都没被读到**。

**为什么它是一条"会自己长大"的规矩**：每踩一次坑就加一条 → 加得越多、读到的越少 → 越容易重犯 → 又加更多条。
**它和功能数量没有直接关系，但它和"越做越慢"有直接关系**：读不到的规矩等于没有。

**做法（2026-09-20）**：
- 根目录 `AGENTS.md` 只留**每天都要照做**的（红线、工作方式、当前状态、命令、判据索引），**上限 48 KB**；
- 讲过程的正文搬进 `docs/rules/`，按主题八册，**内容与拆之前逐字相同**（搬的是正文，不是摘要）；
- `AGENTS.md` 里有一张**索引表**：要动哪个区域，先读哪一册；
- **`check_apex_docs.sh` 机械检查四件事**：① 根文件 ≤ 48 KB；② 索引里提到的文件都存在；
  ③ `docs/rules/` 里没有"没人索引"的分册；④ 一串**关键章节标题**在"根文件 + 分册"里仍然找得到（防丢内容）。

⚠️ **判据**：**一个文件"读不完"不该是静默降级。** 它要么被拆小，要么让门红——因为没人会注意到
"这次的规矩比上次少读了一半"。

## ⚠️ 写脚本时的三个坑（2026-09-20 实测，都是这次拆文档时踩的）

1. **本机的 PowerShell 会把无 BOM 的 `.ps1` 当 ANSI 解码**（解析期就错，不是运行时）。
   实测：一个带中文注释的切分脚本，**`powershell -File` 跑出来是一堆 parser error**，报错信息里的中文全是乱码。
   - **对策**：带中文的东西**不要放进 `.ps1`**。脚本保持 **ASCII-only**，中文写进数据文件（`.md`/`.txt`），
     脚本用 `[System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))` 显式按 UTF-8 读。
   - 同一个脚本用 harness 的 `pwsh` **直接执行**就不会踩到——但"能跑"和"换个调用方式还能跑"是两件事。
2. **PowerShell 取"数组的数组"会塌一层**。实测：`r=@(@(349,509))` 用 `$p.r[0]` 取出来是 `349`，
   于是循环把 349 和 509 当成两个区间，**静默生成一个 9 行的空文件**（没有任何报错）。
   - **对策**：需要"成对/成组"的数据就用**扁平表示**（`349,509, 738,798`），
     并且**每次都验证产物的行数或字节数**——"没报错"从来不是证据。
3. **`Set-Content` 不带 `-Encoding` 会按 ANSI 重写整个文件**（Windows PowerShell 5.1 的默认行为）。
   实测：用它做一次"读-改-写"（本意只是把 `BUDGET=49152` 改成 `1024` 再改回来），
   **同一个文件里的中文被整片吃掉**，而且**不报错**：脚本照样能跑，只是中文注释变成乱码，
   文件从 UTF-8 变成 GBK（字节数明显变小是唯一线索）。
   - **对策**：改文本一律 `[System.IO.File]::ReadAllText/WriteAllText($p, $t, [System.Text.UTF8Encoding]::new($false))`；
     能用编辑工具就别让 shell 的"默认编码"经手。
   - **判据**：**改完文本文件先量一次字节数**（明显变小 = 编码被换了），再看一眼里面的中文。

## 私有拷贝怎么才不打扰用户：两个只给测试用的开关（2026-09-20 实测）

**问题**：装配层每一扇门都启动**自己那一份**整程序（门绝不能拿用户正在用的那份做实验），一次交付要起 **18 次**。
每次都在托盘里放一个图标、几秒后再拿走——用户看到的就是「**反复运行又杀掉（托盘图标反复出现几次）**」，
而且其中一扇门（`check_reaper_live`）**开着一个真实面板窗口 42 秒**（用户的原话：「中间还不断的弹窗打扰用户」）。
实测一次交付：**257 秒、20 次启动 / 19 次停止**（采样器每 250 ms 数一次窗口类）。

**做法**：两个环境变量，和 `APEX_ACCEPT_INJECTED` 同一族（进程启动时读一次、从不写、不是设置、部署的副本永远不会带上）：

| 变量 | 作用 | 谁在用 |
|---|---|---|
| `APEX_NO_TRAY=1` | 宿主**不往托盘放图标**，日志写 `tray: suppressed (...)` | **除 `check_apex_icons` 以外**的每一扇启动私有拷贝的门 |
| `APEX_NO_WINDOW=1` | 面板**永不显示窗口**（进程照跑、页面照跑、回调照跑，只是不 `ShowWindow`） | `check_reaper_live`、`check_apex_shutdown`、`check_apex_flash` ——**所有**起面板的门 |

⚠️ **为什么 `check_apex_icons` 是例外**：它断言 `tray:` 那行日志里的 `icon=`（"宿主到底向 shell 要了哪张图"），
把托盘关掉就没得验了。**一扇门需要看的副作用，就不能替它关掉。**

⚠️ **而另外三扇看起来"需要看得见"，其实不需要——判据是它到底读什么**：
- `check_apex_flash` 读的是 `apex-settings.log` 里的 `webview background:` 行（面板交给 WebView2 控制器的颜色），
  那行在**控制器创建时**就写了，跟窗口有没有显示无关；
- `check_apex_shutdown` 读的是**进程**（宿主退出后面板和它起的浏览器子进程是否都没了）；
- `check_reaper_live` 读的是宿主与面板的**日志**。
**用户 2026-09-20 报的"中间有弹了三次窗口"就是这三扇**（flash 明暗各一次 + shutdown 一次）。
现在一次交付**一个窗口都不弹**。

⚠️ 另外两个夹具**本来就不可见**，别再"顺手"给它们加东西：假 REAPER 的窗口是 **0×0**（`apex_reaper_fake.cpp` 里写着理由），
接收器是 **`WS_EX_LAYERED` + 全透明**（能命中测试、什么都不画，`apex_receiver.cpp` 里同样写着理由）。

**判据**：**一个副作用如果没有任何门在读它，就不要让它出现在用户的屏幕上。**
反过来也成立：**门在读的副作用，一个都不许替它省掉。**

⚠️ **还有一条撞出来的事实（差点让我做出错误的设计）**：**私有拷贝不可能和用户的 Apex 并存**——
用户定的规则是「进程只能有一个Apex.exe」，认的是**可执行文件名**（`settings_ipc.h` 的 `WindowOwnedByExecutable`），
不是目录。所以"让不注入滚轮的门和用户的 Apex 一起跑"这条路**根本不存在**：两个宿主 = 每一下滚轮两个钩子。
装配层必须**整段时间清场**，用户那几分钟里没有 Apex 是**必然**的，只能靠**减少要起宿主的门**来缩短，
不能靠共存。（`AGENTS.md` 里曾有相反的一段话，是旧规则的残留，已改掉。）

## 设置界面拆成三个源文件 + 一个嵌入产物（2026-09-20）

`apex/ui/panel.html` 曾经是 **3,216 行**（559 行样式 + 2,594 行脚本 + 63 行标记），改一处 UI 要在里面翻半天。
现在：**外壳**（`panel.html`）+ **`panel.css`** + **`panel.js`**，`build.sh` 在打包资源之前把它们拼成
`build/panel.built.html`，`panel.rc` 嵌的是那一份。

⚠️ **页面字节一个都没变**：拼出来的文件是 **3,224 行**、四个标签在同样的行号，
而且与**部署目录里那份 exe 内嵌的页面**逐字节相同（187,810 字节）。这就是这条改动的验收判据——
拆文件不该改变送出去的东西。

⚠️⚠️ **读页面的人必须读"拼出来的那一份"**，不能读外壳：外壳里没有 CSS（比色门会找不到颜色）、
`<script>` 里只有一个占位注释（DOM 桩探针会**通过**，因为空脚本不报错——**一扇测试空东西的门**）。
所以 `check_apex_palette` / `check_apex_flash` / `check_apex_modular` / `check_reaper_note` 与五个 JS 探针
现在都指向 `build/panel.built.html`。

⚠️ **而这次真的踩到了"从另一个路径猜路径"的坑**：`apex_palette_probe.js` 里 `icons.h` 的位置是
**从页面路径推出来的**（`…/ui/panel.html` → `…/icons.h`）。页面一搬家，那个替换就匹配不上了，
**探针于是把"页面自己"当成了 icons.h**，七条断言报 "not found"，而被读的页面完全正常。
→ **判据：一个文件的路径如果是从另一个路径推出来的，它就是一个"必须同步的第二处"。**
现在 `icons.h` 由调用方**点名**传进来（`check_apex_palette.sh` 的第三个参数），推不出来了。

## ⚠️ 重写"唯一一份"文档之前，先留一份副本（2026-09-20 的教训）

拆 `AGENTS.md` 那次：**原文是唯一的一份**（这个项目没有 git，`versions\` 里也不放它），而我是**直接覆盖**写的。
事后要证明"一个字都没丢"时，手上已经没有原文可比了——只能靠**动手前记下的那张「标题 + 行号 + 累计字节」表**，
以及"每个片段切出来的行数对得上"这两条间接证据（这次两条都验过：53 个标题一个不少、8 个分册行数全部吻合）。

**判据**：**凡是"把 A 拆成 B、然后覆盖掉 A"的动作，先 `cp A A.before-split`**（放 `build/` 之类的地方，事后再删）。
这和 §一之二 里"刷新快照不是 `rm -rf` 再抄一遍"是同一个错误家族：
**你以为你在整理，其实你在删掉唯一的历史。**

## 一次交付选哪些门：按"变了的产物"决定（2026-09-20）

**背景**：用户实测另一个项目的部署 **2 分钟不到**、中间没有多余的运行测试；而本项目**3 个插件却要 5 分钟**，
中间还不断弹窗。实测一次 `deploy.sh --gated`：**257.7 秒、20 次宿主启动 / 19 次停止**。
分三段花的钱：构建 ~5 s ＋ 构建层 42 s ＋ **装配层 214 s**（九扇门，每扇都要起一份整程序）。
（2026-09-22 加了第十扇 `check_apex_flyout`：从 PowerShell 量到的整轮是 **169 s**，其中含约 1 秒的 Git-bash
启动——所以真实增量约 10–15 s，没有重跑一次 bash 内计时去把这张表钉死，别把 169 当成 bash 里的数。）

**做法**：`apex/deploy.sh` 在跑门之前先算**"这次交付到底变了什么"**——把 `build/apex` 与部署目录**逐字节比**，
再据此选门（`test/run_all.sh --assembly --set <none|panel|all>`）：

| 变了的产物 | 门集 | 实测 |
|---|---|---|
| 什么都没有（只改了文档、脚本注释等） | `none`：只跑构建层 | **46 s**，而且**用户的 Apex 一次都没被停**（没有门要起） |
| 只有 `apex-settings.exe` | `panel`：`flash` + `shutdown` + `reaper_live` | **80 s**（其余七扇打印 SKIP） |
| `apex.exe` 或任何一个功能 DLL | `all`：十扇全跑 | **155 s 上下**（九扇时是 140 s） |

⚠️ **判据是产物，不是源码时间戳**：产物就是"要送出去的东西"，与复制那一步用的是同一个比较（不用第二份真相），
也不需要状态文件（不会漂）。⚠️ **含糊就全跑**：`apex.exe` 装着钩子、托盘、IPC 服务端与配置写入，
而功能 DLL 会改变宿主对滚轮的判定（`decision.h`），所以这两者一律 `all`。`--full` 强制全跑。
⚠️ **跳过的门一定打印出来**（`SKIP (not in the 'panel' set)`）——一套悄悄少跑的门，比一套慢的门糟得多。

**顺带按 Lertaro 那条规矩改了复制**：只覆盖**真的不一样**的文件（"只覆盖真正变化的产物…覆盖面越窄，失败面越小"），
日志逐行写清 `unchanged, left alone`。**ABI 版本变了就必然全变**（版本号编在产物里），所以字节比较已经覆盖了那种情况。

## ⚠️ 把固定 sleep 换成等条件：57 秒 → 15 秒，以及三个真实的坑（2026-09-20）

工具在 `test/lib_procs.sh`：`apex_wait_for` / `apex_wait_line` / `apex_wait_line_gt` / `apex_count_line`。
装配层的固定 sleep 从 **57 s** 降到 **15.5 s**；剩下的全部是"这一段时间里什么都不该发生"那种**测量**。

⚠️⚠️ **坑一：条件必须是"这一步"的，不能是"文件曾经说过"。**
REAPER 那一扇等的是 `not running -- telling the panel`，而宿主**启动时**就写过一行（"the first report"）——
于是等待立刻返回，真正的通知落进下一节的安静窗口，被报成"宿主在不停地念叨"。
**判据：同一句话在一轮里会写多次时，要等的是"计数增长"（`apex_wait_line_gt`），不是"这行存在"。**

⚠️⚠️ **坑二：`grep -c ... || echo 0` 会打印两个 0。**
`grep -c` **没匹配时既打印 0 又返回 1**，所以那个惯用法输出 `"0\n0"`，而 `[ "0\n0" -gt 0 ]` 是 **bash 报错**（不是"假"）——
条件永远不成立，等待**烧掉整个预算**却一句话都不说。实测代价：一扇门 14 s、另一扇 32 s。现在统一走 `apex_count_line`。

⚠️⚠️ **坑三：用一个"贵的轮询"去等一件"不该发生"的事，等于把超时全烧掉。**
`check_apex_single` 里"第二个拷贝**不该**出现"是拿 `PidsIn` 轮询 60 次实现的，而**每次 `PidsIn` 都要起一次 PowerShell**
（实测 0.39 s）：60 × 0.53 s = **32 s**，而且那件事本来就不发生，**每一轮都必然跑满**。
→ **"观察缺席"是一次有界的安静窗口 + 一次检查**，不能是轮询。（它最后那道 `apex_count` 断言仍然兜着"迟到者"。）

**同一类账探针里也有**（`_diag/apex_edit_abi_probe.cpp` 一次 47.6 秒）：`Ask()` 会**等一份文档**（最多 3 s），
而 `listOp` / `setControl` **只回一个状态码、根本不发文档** → 十几个调用各自等满 3 s。
现在文档类命令走 `Ask`、状态类走 `Tell`（只发不等）；"等到文件里出现/消失"改成**轮询文件**；
"观察一次不该发生的写入"改成**等文件 mtime 变化**（有证据才叫观察缺席）。那一扇 **56 s → 10.8 s**。

**判据**：**门里出现 `sleep N` 时，先问它是"等一件事"还是"测量一段时间"。** 前者一律换成条件；
后者留成 sleep 并在旁边注明为什么。本项目现在只剩 15.5 s 的 sleep，全部是后者（安静窗口、指针沉降、重试间隔）。

## ⚠️⚠️ 一扇门只覆盖了四分之一的功能：MediaControl 的空页面（2026-09-22）

用户的一句话：「**媒体控制页面是空的**」。这句话在这个项目里是**有前科**的——`check_feature_chart.sh` 自己的头部注释
就写着它为什么存在："a document the page rejected outright … the user-visible symptom was the same as 'the feature
sent nothing': an empty card"。而那扇门**这次没有响**，原因有三个，每一个都值得单独记住。

**一、它只测一个功能。** 脚本里硬编码着 `Plugins/SmoothWheel/SmoothWheel.dll`。四个功能里，
只有轮子的文档被解析过；KeepAwake、AutoIME、MediaControl 的文档**从来没被任何门读过**。
现在它遍历 `build/apex/Plugins/*/*.dll`，并且**数了自己检查了几个**——一个目录都没找到也会红。

**二、"括号平衡"不是"它是 JSON"。** 探针里那圈括号/引号走查（`JsonBalanced`）是**故意**写的，
也真抓到过当年的两个结构错误，但 MediaControl 交出来的文档是 `]},,{`——**括号完美平衡**，
多出来的那一个逗号它看不见。所以文档现在还要交给**真的解析器**（`node -e 'JSON.parse'`，
和 `check_apex_panel.sh` / `check_reaper_note.sh` 用的是同一个工具），失败时打印**字节位置和附近的原文**：

```
FAIL: the document is not JSON -- Unexpected token ',', ..."ff":0}}]},,{"id":"of"... is not valid JSON
```

⚠️ **两道检查都留着，因为它们失败的方式不同**：走查抓"少了一个括号"，解析器抓"多了一个逗号"。

**三、门违反了 ABI 的调用顺序，而功能因此段错误。** 探针原本**故意不调 `init`**，注释写着
"settingsJson works from the feature's defaults"——那是**关于一个功能的观察，被当成了契约**。
ABI 说的是 `init` 之后功能的状态才算建好，而 KeepAwake 和 MediaControl 的 `settingsJson` 都要进
`init` 里创建的那把锁。把这扇门指向每个功能之后，**两个功能当场 SIGSEGV**。
现在探针按契约调用 `init`（并给每个功能一个 `build/` 下的 scratch 目录放它的设置文件）。

**判据（三条，都是这次的）**：
1. **遍历，不要点名。** 一扇门里出现某个功能的名字，它就只能保护那一个功能——而"加一个功能 = 只写一个文件夹"
   意味着**新功能不会去改这扇门**，于是它永远不被检查。
2. **结构检查和解法检查都要**（括号平衡 × 真解析器）。
3. **门要按契约调用被检查的东西。** 用非契约的方式调用而它崩了，那不是功能的 bug，是门在测一个不存在的用法——
   但代价是一样的：一条红/崩的信息，读起来像产品坏了。

⚠️ **还有一条流程上的**：这扇门是**构建层**的，所以它本该在**部署之前**就红。它没红，因为上面三条。
构建层的意义就是"数据模型在交付前验完"（用户定的），而这次漏的就是它该管的那一类。
