### 3.7.2 退出：关一个，退干净（**别的不许留下**）

用户的要求：「主界面在托盘进程退出，也要跟着关闭，插件进程什么的要退干净」。两条路都要能到终点：

- **面板发现自己该走**（宿主被强杀、崩溃时走这条）：`ui_webview.cpp` 那个 2 秒轮询发现宿主没了 →
  通知页面 → **`PostMessage(WM_CLOSE)` 关掉自己**。**不能在自己的 `WM_TIMER` 里直接 `DestroyWindow`**
  ——那是从窗口自己的消息里拆自己；`PostMessage` 排到下一轮，且**和用户自己点关闭是同一条路**。
- **宿主自己在退**（用户点退出时走这条）：`main.cpp` 的收尾**先请面板关**（`PostMessage(WM_CLOSE)` +
  **最多等 2 秒**），**超时才 `TerminateProcess`**。为什么不一上来就杀：面板是 WebView2 宿主，
  它的浏览器子进程是在 `WM_DESTROY` 里由 `Close()` 收掉的，**`TerminateProcess` 跳过这一步**，
  浏览器进程就得自己去发现爸爸没了——它们会，但不是立刻，于是"程序关了，进程还在那儿"。
  **挂死的面板照旧被杀**（这正是面板单独一个进程的原因），所以这个等待不会拖住退出。
- **`test\check_apex_shutdown.sh` 验它**，用 `WM_CLOSE`（**不是 `taskkill`**：`/F` 跳过所有收尾，
  而那正是被测的东西）。浏览器子进程按 **user-data-dir** 数，不按进程名（§6.1）。

### 3.7.2.1 ★ 预热：把"浏览器启动的 0.55 秒"花在用户挑菜单的时候

用户对上面那条（窗口等页面画好才显示）的反应是"慢了一点点，但感观舒服、能接受"，并问还有没有更优解。
**量出来的账**（改名副本实测，没碰用户在跑的那份）：面板从启动到窗口出现 **暖数据目录 537–658ms**、
**首次运行（WebView2 数据目录新建）1430ms**；这段时间全是 WebView2 自己启动，**和插件数量无关**。

**做法**：`TrayMenu()` 里 `TrackPopupMenu` **之前**调 `PrewarmPanel()` —— 用户从"打开菜单"到"点到设置"
的那段时间，正好用来起浏览器。两条按名字注册的消息决定它的命运（`settings_ipc.h`）：
`ApexPanelShow`（点的是设置）／`ApexPanelDrop`（任何别的选择，包括菜单被点走）。实测：预热后 **SHOW→25ms 出现**、
**DROP→35ms 退出且全程没露过面**；菜单关掉时没被要的看板**不留常驻进程**（60s 看门狗兜底：宿主在菜单开着时死了，
也得自己走）。

⚠️ **三条容易做错的**：
1. **`ShowWindow` 不能从宿主跨进程调**——预热中的面板可能还没画完，那一调就是把"空白矩形"放出来，
   正是隐藏窗口要避免的东西。**只有页面知道它画好了**，所以只能由面板自己决定何时出现，消息只是"该出现了"。
2. **`--warm` 的进程若发现已有面板，一个字都不能做**（尤其不能把它显示出来）：用户只是右键了托盘。
3. **顺序两个标志位**（`g_wantShow`／`g_pageReady`）：用户可能在页面还没画完时就点了设置，
   这时"要显示但还没准备好"必须仍然**保证出现**（`kPanelShowTimer` 兜底），不能变成点了没反应。

**⚠️ 双击托盘图标那条路没有这个待遇**（`WM_LBUTTONDBLCLK` → `OpenSettings()`，早就支持）：
双击之间只有 80–200ms，藏不住 0.55 秒。**用户明确决定：那 0.55 秒接受，不改。**

**常驻是量过之后才决定不做的**（2026-09-19 实测，改名副本）：
**隐藏的预热面板 = 7 个进程、私有内存 ≈173MB、工作集 ≈351MB**（面板自己只占 18.5MB/5MB，其余全是
`msedgewebview2.exe`）；而**宿主 `apex.exe` 私有只有 6.1MB**。为了 0.55 秒把空闲占用抬 28 倍，不值。
SDK 里有 `ICoreWebView2_3::TrySuspend`／`Resume`（`third_party\webview2\include\WebView2.h`），
**能常驻但把内存放掉**——**挂起后降到多少、恢复多久，都没量过**，要做得先实现再量；
用户当时的回答是"不动，保持现在"。以后再想提常驻，先看这两个数。

### 3.7.3 设置：改一下就落盘，不等退出

用户的要求：「插件设置保存可以一直在，不用每次编译都清掉」。**"退出时保存"听着够用，实际不够**：
退出路径是 `WM_CLOSE -> DestroyWindow`，而程序真正的死法是 `taskkill`、崩溃、断电、或者开着不管一星期。
**实测就发生了**：调完参数、进程被杀、下次启动回到默认值。

- **改法是防抖**（`main.cpp` 的 `SettingsTouch` + `APEXWM_SAVE_TIMER`，1 秒）：
  每个改设置的 IPC 命令都踢一下计时器，**重新设置同一个 id 是替换而不是新增**，所以**拖一次滑块 = 写一次**。
  1 秒不是性能参数，它只要**熬过一次拖动**；**每一毫秒都是"被强杀时可能丢掉的那一毫秒"**。
- **热路径毫发无损**：滑块是**按像素**发 `setFeature` 的，如果在处理器里直接写文件，一次拖动就是几百次写。
- **⚠️ 而且「门不许清掉设置」是另一半，那部分是门自己的错**：`check_apex_endtoend.sh` 把自己的
  `apex.ini` **覆盖进 `build\apex\`**（用户被告知可以直接运行的文件夹）并删掉日志；两个门还
  **按进程名 `taskkill /F /IM apex.exe`**，把**用户正在跑的那一份**杀掉——**被杀的进程永远到不了收尾**。
  **两条都已改**：门跑**自己的拷贝**，杀**按路径**。判据写进了 §五 的三条硬规矩。
- **`test\check_apex_persist.sh` 验它**：改一次 → 1 秒后文件里有 → `taskkill /F` → 值还在 →
  并且**`build\apex\` 一个字节没动**。
