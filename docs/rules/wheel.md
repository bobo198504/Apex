### 3.3 ★ 吞不吞滚轮的判定：`apex\decision.h`

**这是 Apex 里唯一一个"坏了就等于滚动彻底失灵"的规则**，所以它被抽成纯函数、可以穷举测试。
不变式：**吞掉 ⇒ 必须有东西补上**。

**它坏过一次**：运行时开关关掉时，钩子仍然吞事件而注入器不发声 → 原格被吃掉、没东西替代 →
滚动完全失灵。而那个开关的本意是"什么都不做"。

⚠️ **那个开关已经被删掉了**（用户要求："托盘右键的'启用'去掉，包括通用设置里的。以后只有插件各自有自己的'启用'"）。
总开关（`apex.ini` 的 `enabled`）和托盘的运行时开关（`g_running`）**都不存在了**。
但**不变式仍然成立，而且不是靠运气**：现在唯一能让 Apex "什么都不做"的方式就是把功能关掉，
而那正好落在下面的第 4 条上。`check_app_swallow.sh` **没有跟着删**——它少扫了两维，但那条会坏的路径
换了个入口依然存在（用户关掉自己唯一的功能 / 唯一的功能加载失败），所以那扇门还在跑，144 组穷举。

评判顺序（**顺序本身是设计，不要重排**）：

1. 自己的注入 → 放行（不能自环；**放行**，不是吞）
2. 别的处理器（REAPER 插件 / **读不到进程**）→ 放行。**UNKNOWN 与 PRESENT 同等对待**：
   猜错的代价是"两个处理器驱动同一个视图"，比"这一格不缓动"严重得多
3. 没有任何可用的功能 → 放行（**这一条就是上面那个 bug 的解药**，也是现在唯一能"关掉 Apex"的路）

⚠️ **黑名单原来在这里（第 2 条），现在不在了**——它搬进了功能自己（见 §3.9）。
**判据没变**：被列入的程序滚轮原样放行。变的是**谁做决定**：以前是宿主在功能之前拦，
现在是功能在自己的 `onWheel` 里拒绝认领，而**拒绝认领 = 放行**（本函数只会说"放行"或"可以问功能"）。
端到端验证过：黑名单里的接收器收到 3 条原始刻度 / +360，不在名单里则是 ~115 条 / +130。

`DecideWheel()` **只会返回"放行"或"可以问功能"**，永远不会自己返回"吞掉"——
吞掉是功能认领之后的结果。这是不变式成立的结构性原因。


### 3.6 抓钩与注入的五条硬约束（都实测过，别改）

1. **注入的事件必须最先丢弃。** 自己的输出会回到钩子里；`LLMHF_INJECTED` 是主判据，
   `g_injecting` 是第二道。**自环是唯一"既看不见又无限"的故障。**
   - ⚠️⚠️ **但 `g_injecting` 绝不能拿来拦真实滚轮**（2026-09-18 修，用户报「快速滚动会出现跳」）。
     它曾经写成 `if (g_injecting == 0 && (...))` —— `g_injecting` 在 `SendInput` **期间**为 1，
     而宿主每 4 ms 就注入一次，于是**约 1/4 的时间里到达的真实滚轮被整个跳过**，原样砸进接收方：
     一整格 120 delta 夹在平滑流（每条约 1 delta）中间。**那就是用户看到的"跳"。**
     **真实的格根本不带 `LLMHF_INJECTED`**，`!injected` 这一条本来就拦住了自环；
     `g_injecting` 只在**测试模式**（`APEX_ACCEPT_INJECTED`，它故意忽略那个标志）里才是必需的，
     因为那时自己的输出和测试注入器发的格**确实无法区分**。所以判断改成：
     `if (!synthetic || (acceptSynthetic && !ourOutput))`。
     **判据**：真实轮子 `!synthetic` → 永远处理；自环 `synthetic && ourOutput` → 永远丢。
2. **吞不吞的判定必须在钩子里做**（从缓存读），不能等到时钟——那时原格已经落地了。
3. **`SendInput` 只能在专用线程调用。** 在消息驱动的调用里调它，它会等一个自己阻塞住的消息循环：
   **实测 1001 ms**，这就是当初"卡一下然后猛冲"的全部原因。
4. **时钟用高分辨率可等待计时器，不用 `SetTimer`。** `SetTimer` 被钳在 ~15.6 ms（实测），
   4 ms 时模型每帧约 0.75 delta（细腻），15.6 ms 时是 13–18（肉眼可见跳）。
   （⚠️ 唯一的例外是**面板存活性轮询**那种纯通知计时器：它没有这个要求，用 `SetTimer` 是对的。）
5. **⚠️ 跨线程发布的缓存必须整体读、整体写。** 目标缓存（`pid`/`exe`/`handler`）由时钟线程**就地改写**，
   而钩子线程在读它。原来那种"先整块赋值、再置 valid"的写法**中间窗口是危险的**：
   读者可能拿到「**新程序的 pid + 旧程序的 handler**」——而最坏的那一组合是
   **一个有滚轮处理器的程序被读成 handler=ABSENT**，于是判定允许功能去平滑它，
   正是 `decision.h` 说"比不缓动严重得多"的「两个处理器驱动同一个视图」。
   **修法是 seqlock**：写时序号变奇、写完变偶；读者前后各取一次号，不一致就重试，
   重试用尽就当**目标未知**（功能拒绝认领 → 滚轮原样放行，是安全方向）。
   **注释曾声称"缓存只读一次"**——而代码是两次独立读，**注释和代码说的是两件事**。

### 3.6.1 曲线动画：实时靠"边缘立刻发"，合并靠时钟

用户问过「曲线动画有办法做到实时吗」——**能，而且已经做了**。链路与两条通道：

```
功能 onWheel（输入路径）-> ApexHost::activity() -> 宿主 -> 面板进程 -> 页面 __apexActivity(n)
```

- ⚠️ **钩子跑在主线程上**（低级钩子由安装它的线程回调，而安装者是 `WinMain` 的线程）。
  所以 `HostActivity()` 里**可以直接 `PostMessage`**：它只是入队，不等面板，不会阻塞输入路径。
  （早先注释写着"no sends"，那是**没核实就写的**。）
- **边缘（静止→开始滚）立刻投递**：用户按下滚轮的那一下必须马上有反应，等 30 ms 时钟纯属白等。
- **其余由时钟合并（30 ms）**：持续滚动或自由滚轮每秒上百个事件，**一个事件一次跨进程脚本调用
  是不行的**，而屏幕一帧也显示不了更多。
- **两条通道用 `InterlockedExchange` 抢计数（claim）**，所以**一个事件恰好投递一次**——
  边缘和时钟会竞争，单纯的"先读后写"会重复计数。
- 面板句柄**从 IPC 请求的发送者里学**（`SettingsPanelSeen`，`WM_COPYDATA` 的 WPARAM 就是面板自己），
  **不在输入路径里 `FindWindow`**——那是在枚举窗口。

### 3.6.2 三个模型，各管一件事（**分层就是这里的全部**）

用户的原话：「主模型不要变，**投递层前面那个新加的小模型**，REL 再拉长点 200ms，并且是固定值」。

```
shared\            主模型（插件 src\ 的副本，一个字节都不动）
  ↑ 决定：一格走多远（速度预算），以及把量摊开多久（窗口）
common\release.h   ★ 小模型：窗口该多长（+200ms 固定）
  ↑ 决定：单个 = Glide；滚动中 = Glide + 200ms
apex\host_win.cpp  投递层：把 core 交出来的量送进接收方（SendInput）
```

- **为什么小模型是独立一个文件**：窗口这一个数**同时干两件相反的事**——它是**单个滚动的渐入**
  （要短，长了像拖泥带水），也是**滚动的收尾长度**（要长，用户要的是「让滚动的时候，收尾拉长的」）。
  一个数不能又短又长，所以把它抽成决策、放在主模型和投递层中间。`common\release.h` 只有三个纯函数。
- **⚠️ 它和**被删掉的那个 `tail`** 不是一回事**，两处区别是这次改动的全部要点：
  1. **固定值**，不随速度缩放（旧的 `windowMs = glide*(1+tail*u)` 把收尾变成了速度表，油门一松长度就变）；
  2. **不是设置**，没有滑块、不写进 ini（没有可调项，也就没有和 Glide 失配的可能）。
- **⚠️⚠️ 两条轴，各拿一个永不改变的长度。这不是优化，是修 bug。**（2026-09-18，用户报「快速滚动会出现跳的
  现象，应该跟最后加的这200ms有关」——**他说对了，两处都对**。）

  **当时的写法**：一条轴，`windowMs_` 在滚动被识别时从 200 变 400。
  **为什么这必然跳**：`anim3::Glide::Tick` 每次只拿**一个**窗口长度，并拿它去除**每一个**在飞的窗口的
  年龄（`w` 是全局的）。所以长度一变，**已经在飞的那条**（才走了 20ms）剩下的量立刻被摊到两倍时间里——
  速率**一帧内减半**。实测（25ms 间隔，第 7 帧）：`0.4423 → 0.1475`，**塌 67%**，然后再爬。越慢越惨：
  100ms 间隔塌 76%，180ms 边缘塌 90%。那就是"跳"。

  **现在的写法**：`lone_` 和 `roll_` 两条轴，每个消息按自己的 gap 进其中一条，**两条的长度都从头到尾不变**，
  输出是两者之和。长度成了**那条窗口自己的属性**——模型本来就是这个意思（`Params.payoutEase` 就是按窗口存的），
  只是"长度"以前没跟着走。实测：同样的位置，突变从 43–90% 降到 **1.00x**（就是平滑坡道上下一步）。

  **⚠️ 那个"长度只能变长、不能在还有窗口在飞的时候缩短"的补丁（latch）已经删了**——它防的危险在没有
  两条轴的时候就够不着了。删掉它还顺手修好一个副作用：以前停顿后再滚，第一条会沿用**上一次滚动**的长窗口，
  于是新动作的第一格发飘。

  **判据**：`check_app_release` 第 5 节量**滚动被识别的那一帧**（不是全曲线的最大值——那三版指标都测的是
  指标自己：收尾的最后一帧、坡道的加速都被误报过）。**这个门验过两端**：把单轴写回去，它报 **30x FAIL**；
  正确的核心 **1.02x PASS**。判据 2.0 夹在中间。
  （⚠️ 第一次写这个门时索引差了一帧，坏的核心也能过——**是"故意改坏看门会不会红"发现的**，
  一个不会红的门比没有门更糟，因为它算一个。）
- **⚠️「滚动中」的判据是「会不会重叠」（`gapMs < baseWindow`），不是速度。** 这样两层说的"滚动"是同一件事：
  主模型自己的 `PayoutEaseFor` 用的就是同一个条件，两处不可能对"这条消息算不算滚动"有分歧。
- **⚠️ 图里画的是滚动的窗口。** 曲线有膝盖和爬坡，那两段只在窗口重叠时存在——所以那张图**本来就代表滚动**，
  `AddCurve` 用的是 `ReleaseRollWindowMs(...)`。用单个的窗口画会让图的宽度短于它代表的那段运动。

### 3.6.3 我们的滚轮不能平滑我们自己面板上的滚轮

**每个滑块都把滚轮当"加一格"用**（用户要求：「插件拉杆、旋钮（以后也有）支持滚轮直接改值」）。
这只有在滚轮**原样到达**时才成立：平滑过的滚轮是宿主重新注入的一串小消息，一格会变成几十条，
滑块会把每一条都当成一格，**数值直接跑飞**。所以 `decision.h` 里它是**第 2 条**（在"别的处理器"之前）：

```
1. 自己的注入        -> 放行
2. 我们的设置面板     -> 放行   ★ 不是"别人占了"，是"这条滚轮另有职责"
3. 别的处理器/未知    -> 放行
4. 没有可用功能       -> 放行
```

- **认得出来靠窗口类，不靠 exe 名。** 页面真正的属主是 `msedgewebview2.exe`（共享设施），
  按 exe 名判等于什么都没判；而点进去的**顶层窗口**是 `ApexSettingsWnd`——实测
  （`_diag\apex_hit_probe.cpp`）`WindowFromPoint` 给 `Chrome_RenderWidgetHostHWND`，
  `GA_ROOT` 给 `ApexSettingsWnd`。**必须连 `GA_ROOT` 一起取**，`TargetUnderCursor` 因此多一个出参。
- **一行是 `strcmp(类名, APEX_SETTINGS_WND_CLASS)`**，和程序里别处认这个窗口的方式同一个。

### 3.6.4 便携程序：**一台机器只许一个 `apex.exe`**（这条规则改对过一次）

- **窗口类名不唯一。** 程序可以整个文件夹拷走，两份拷贝注册**同一个** `ApexSettingsWnd` /
  `ApexHostWnd`；`FindWindowA` 返回哪个是碰运气。
- **实测的后果**：从第二份拷出来的面板 `FindWindow` 到第一份的面板 → 把它提到前面 → **自己退出**。
  于是第二份永远没有面板，而用户看着的是**另一份的设置**，没有任何地方报错。
  **写关机门的时候撞上的**，不是猜的。
- ⚠️⚠️ **判据曾经是"同一个目录"，现在是"同一个可执行文件名"——而且不能改回去。**
  早先的规则是"同一个文件夹 = 同一份安装"，于是两个文件夹被当成两套程序、**允许并存**。
  用户把它收紧成**一台机器一个 `apex.exe`**（原话：「进程只能有一个Apex.exe」），理由是功能性的：
  Apex 全局挂钩滚轮，两个宿主就是每一下滚轮两个钩子，各自吞掉自己看到的再注入自己的输出，
  第二个还会看到第一个注入的事件——正是 `decision.h` 说的"两个处理器驱动一个视图"。
  实现是 `settings_ipc.h` 的 `WindowOwnedByExecutable`：**只比 exe 名，不比目录**。
  ⚠️ 文档里的 `SameInstallDirectory` / `FindOwnWindow` 这些名字是**旧规则的残留**，代码里已经没有它们了。
- **`FindWindowA` 只返回一个窗口**，所以要**枚举**：按类名找候选、再用 `WindowOwnedByExecutable` 认出自己的。
  找不到不是错误——那是"这一份的另一半没起来"，面板照常启动并如实报告"宿主未运行"（**对本份而言是真的**）。
- ⚠️ **这条规则直接决定了门的代价**：私有拷贝**不可能**和用户的 Apex 并存，所以装配层的门必须**先清场**，
  而那几分钟里用户是没有 Apex 的。想缩短这个窗口，只能**减少要起宿主的门**，不能靠"让它们共存"。
